STRUCTURE DU PROJET SENEMALI API
================================

Senemali API est une API REST developpee avec Java 21 et Spring Boot 3.3.5.
Elle expose les fonctionnalites de la plateforme agricole Senemali pour les
applications web et mobiles. La persistance utilise Spring Data JPA et MySQL.

1. RACINE DU PROJET
-------------------

pom.xml
    Configuration Maven : dependances, version Java, plugins Spring Boot,
    compilation et traitement des annotations Lombok.

mvnw / mvnw.cmd
    Maven Wrapper pour construire et tester le projet sans installer Maven
    manuellement (les prerequis Java restent necessaires).

HELP.md
    Aide de demarrage generee par Spring Initializr.

src/main/java/com/senemali/api/
    Code source Java de l'application.

src/main/resources/
    Configuration, fichiers statiques et templates utilises au runtime.

src/test/java/com/senemali/api/
    Tests automatises du projet.

2. ORGANISATION DU CODE JAVA
----------------------------

SenemaliApiApplication.java
    Point d'entree Spring Boot. Demarre l'application et le contexte Spring.

config/
    Configuration transversale de l'application : securite, CORS, MVC,
    initialisation des donnees et documentation OpenAPI.

controller/
    Points d'entree HTTP de l'API. Chaque controleur recoit les requetes,
    valide ou transmet les donnees au service approprie, puis retourne une
    reponse HTTP. Les controleurs couvrent notamment l'authentification,
    les acheteurs, agriculteurs, commandes, cultures, produits et services.

 dto/request/ (package reel : dto/request/)
    Objets de donnees recus par l'API. Ils definissent les champs attendus
    par les operations et peuvent porter des contraintes de validation
    Jakarta Validation. Exemples : AuthRequest, RegisterRequest,
    AcheteursRequest et AdministrateurRequest.

dto/response/
    Objets de donnees renvoyes par l'API. Ils evitent d'exposer directement
    les entites JPA et permettent de controler la forme des reponses.

entity/
    Entites JPA associees aux donnees persistantes : utilisateurs, acheteurs,
    agriculteurs, fournisseurs, commandes, cultures, produits et autres
    ressources metier. Les relations entre entites sont declarees ici.

enums/
    Types enumeres utilises par le domaine, par exemple les roles, les statuts
    de commande, les statuts de validation et les types de notification.

exception/
    Exceptions metier et gestion centralisee des erreurs HTTP, dont les
    ressources introuvables et le format ErrorResponse.

mapper/
    Conversion entre les DTO et les entites. Les mappers construisent aussi
    les DTO de reponse, sans effectuer de recherche en base ni appliquer les
    regles metier. Les services leur fournissent les entites relationnelles
    deja resolues quand cela est necessaire.

reponse/
    Package de reponses globales partagees par l'API. Le nom est actuellement
    ecrit "reponse" dans le code source.

repository/
    Interfaces Spring Data JPA pour lire, creer, modifier et supprimer les
    entites, ainsi que pour declarer les requetes derivees.

security/
    Composants de securite et gestion des tokens JWT.

controller/FileUploadController.java, serviceImpl/FileStorageServiceImpl.java
    Upload de fichiers via multipart/form-data. En mode local, le stockage est
    fait dans le dossier configure par app.upload.dir. En mode Supabase, les
    fichiers sont envoyes dans le bucket configure par SUPABASE_BUCKET. Les
    images sont rangees par dossier (profils,
    produits, intrants, tutoriels, services, conseils, financements) et
    limitees a 10 MB. Le dossier tutoriels accepte aussi les videos MP4,
    WEBM et MOV jusqu'a 100 MB. Les fichiers ont un nom UUID ; l'URL publique
    pointe vers le fichier sans stocker son contenu dans MySQL. Pour utiliser
    Supabase, definir APP_STORAGE_PROVIDER=supabase ainsi que SUPABASE_URL,
    SUPABASE_SERVICE_ROLE_KEY et SUPABASE_BUCKET dans l'environnement du
    backend. La cle service_role est secrete et ne doit jamais etre exposee au
    client web/mobile ni committee. En mode local, les chemins /uploads/
    sont servis par config/WebMvcConfig.java.

Quantites de stock
    ProduitAgricoleResponse expose deja quantite pour le stock d'un produit.
    IntrantResponse expose egalement quantite pour le stock d'un intrant ;
    IntrantRequest exige une quantite positive a la creation ou modification.
    La quantite d'une ligne DetailCommandeResponse est la quantite commandee,
    tandis que celle renvoyee dans les reponses produit/intrant correspond
    au stock declare pour l'article.

service/
    Interfaces qui definissent les operations metier disponibles.

serviceImpl/
    Implementations des services. Elles coordonnent les repositories et les
    mappers, resolvent les relations, appliquent les regles metier et gerent
    les transactions.

3. PARCOURS D'UNE REQUETE
-------------------------

Client HTTP
    -> Controller : recoit la requete et ses DTO
    -> Service : applique les regles metier et orchestre l'operation
    -> Repository : accede aux donnees via Spring Data JPA
    -> Entites : representent les donnees persistantes et leurs relations
    -> Mapper : convertit le resultat en DTO de reponse
    -> Controller : retourne la reponse HTTP au client

Les identifiants de relations recus dans les DTO sont generalement resolus
par le service avec les repositories. Les valeurs calculees ou gerees par
l'application (par exemple un statut initial, une date ou un montant) restent
de la responsabilite du service.

Commandes : deux parcours distincts
Un ACHETEUR cree une commande de produits agricoles appartenant a un
agriculteur. Un AGRICULTEUR cree une commande d'intrants appartenant a un
fournisseur valide. Une commande ne melange pas produits et intrants et
ne peut contenir que des lignes provenant d'un seul vendeur.

Le client envoie POST /api/commandes avec les details (idProduit ou
idIntrant et quantite). Il ne fournit pas l'id de l'acheteur/agriculteur :
le backend identifie le client a partir du JWT. Le prix et le montant total
sont calcules par le serveur.

ADMIN peut consulter toutes les commandes via GET /api/commandes et les
details par GET /api/commandes/{id}, mais ne cree pas, ne modifie pas le
statut et ne supprime pas les commandes. Les acheteurs, agriculteurs et
fournisseurs consultent leurs commandes/interventions avec
GET /api/commandes/mes-commandes. Un client peut annuler sa commande en
cours ; seul le vendeur concerne peut la marquer LIVREE.
GET /api/commandes/mes-commandes/count renvoie pour un agriculteur ou un
fournisseur authentifie le nombre de commandes distinctes recues pour
ses produits ou intrants.

4. RESSOURCES
--------------

src/main/resources/application.properties
    Proprietes Spring Boot et configuration de l'application. Les secrets et

    ne pas etre publies dans le depot.

    Ressources statiques servies par Spring, si necessaire.

    Templates de vues serveur, si necessaire.

5. TECHNOLOGIES PRINCIPALES
---------------------------

- Java 21
- Spring Boot 3.3.5
- Spring Web pour les endpoints REST
- Spring Data JPA pour la persistance
- MySQL comme base de donnees
- Spring Security et JWT pour l'authentification et la securite
- Jakarta Validation pour la validation des entrees
- Lombok pour reduire le code repetitif
- Springdoc OpenAPI pour la documentation de l'API
- Maven pour la gestion des dependances, la compilation et les tests

6. AUTHENTIFICATION ET SECURITE JWT
-----------------------------------

Principe general
    Angular, Flutter ou Swagger envoie des requetes HTTP a l'API. Le client
    s'authentifie une fois avec son email et son mot de passe. L'API retourne
    un JWT que le client doit ensuite joindre aux requetes protegees.
    L'application est stateless : le serveur ne conserve pas de session
    utilisateur ; chaque requete protegee doit contenir le JWT.

Fichiers principaux

config/SecurityConfig.java
    Configure Spring Security, BCrypt, CORS et les routes publiques. Les
    routes login, inscription, Swagger et health sont publiques ; toute autre
    route requiert un utilisateur authentifie. Active aussi les verifications
    de methodes @PreAuthorize et insere JwtAuthFilter dans la chaine HTTP.

security/JwtAuthFilter.java
    Examine l'en-tete HTTP Authorization. Si sa valeur commence par
    "Bearer ", extrait le JWT, le valide avec JwtUtil, recharge l'utilisateur
    avec UserDetailsServiceImpl et place son authentification dans le
    SecurityContext pour la requete en cours.

security/JwtUtil.java
    Cree, signe, lit et valide les JWT. Le sujet du token est l'email ; le
    token contient aussi le role et ses dates d'emission et d'expiration.
    La cle de signature et la duree de validite viennent des proprietes
    jwt.secret et jwt.expiration. Un JWT est signe, mais son contenu n'est
    pas chiffre : ne pas y placer de mot de passe ou de secret.

Fonctionnement du JWT
    1. L'utilisateur envoie POST /api/auth/login avec son identifiant et son
       mot de passe. AuthServiceImpl retrouve son compte, compare le mot de
       passe avec BCrypt et refuse une connexion si le compte est desactive
       ou si un fournisseur n'a pas ete valide.
    2. Apres authentification, JwtUtil cree un token signe avec HS256. Le JWT
       comprend un en-tete, des donnees (email comme sujet, role, dates de
       creation et d'expiration) et une signature calculee avec jwt.secret.
       La duree jwt.expiration configuree actuellement est de 86 400 000 ms,
       soit 24 heures.
    3. Le client envoie ce token pour les routes protegees dans
       Authorization: Bearer <token>. Le filtre JwtAuthFilter verifie la
       signature et l'expiration, extrait l'email et recharge l'utilisateur
       depuis la base. Il verifie aussi que le compte est encore actif, puis
       etablit son identite et ses autorites pour cette requete.
    4. SecurityConfig exige une authentification pour toute route qui n'est
       pas dans la liste publique. Les annotations @PreAuthorize des
       controleurs ajoutent les controles de role et de propriete de donnees.
       Une authentification manquante ou invalide donne HTTP 401 ; un compte
       authentifie mais non autorise donne HTTP 403.

    Un JWT signe garantit que son contenu n'a pas ete modifie, mais ne le
    rend pas secret : toute personne qui obtient le token peut lire ses
    donnees. Ne pas y mettre de mot de passe ou de donnee confidentielle. Le
    role contenu dans le token n'est pas la seule source d'autorisation :
    les autorites sont rechargees depuis le compte en base a chaque requete.
    L'application etant stateless, elle ne conserve pas de session ni de
    liste de tokens revoques ; la deconnexion cote client consiste a effacer
    le token. Le renouvellement JWT n'est pas implemente actuellement ; la
    propriete jwt.refresh-expiration seule ne constitue pas un endpoint de
    renouvellement.

    La propriete jwt.secret est une cle de signature sensible : en production,
    elle doit etre forte, configuree hors du depot (par exemple par variable
    d'environnement ou gestionnaire de secrets), et ne jamais etre communiquee
    ni inscrite dans les logs. Transmettre les tokens uniquement via HTTPS
    et les conserver dans un stockage adapte a la plateforme cliente.

security/UserDetailsServiceImpl.java
    Recherche l'utilisateur par email et fournit a Spring Security son hash
    de mot de passe et son autorite ROLE_<role>. Un compte inactif est
    desactive ; un fournisseur doit aussi avoir le statut VALIDE.

security/JwtAuthEntryPoint.java
    Retourne une reponse JSON HTTP 401 quand une requete protegee ne presente
    pas une authentification valide.

security/AccessControl.java
    Fournit des verifications utilisees par @PreAuthorize pour verifier
    l'utilisateur courant, son role et la propriete d'une ressource
    (commande, produit, intrant, notification ou association de culture).

controller/AuthController.java
    Expose les routes d'authentification : POST /api/auth/login,
    POST /api/auth/register et GET /api/auth/me.

serviceImpl/AuthServiceImpl.java
    Effectue la connexion, compare le mot de passe avec son hash BCrypt,
    verifie que le compte est actif et que le fournisseur est valide, puis
    demande a JwtUtil de creer le token. A l'inscription, encode le mot de
    passe avant de l'enregistrer. La creation publique d'un ADMIN est refusee.

Protection des mots de passe en base
    Les mots de passe ne sont pas chiffres de maniere reversible : ils sont
    haches avec BCrypt avant leur enregistrement dans la colonne mot_de_passe
    de la table utilisateurs. SecurityConfig configure BCrypt avec un facteur
    de cout de 12. BCrypt genere un sel aleatoire et l'inclut dans la valeur
    hachee ; deux encodages d'un meme mot de passe peuvent donc etre differents.
    Lors de la connexion, AuthServiceImpl utilise passwordEncoder.matches()
    pour verifier le mot de passe saisi a partir du hash stocke. Le mot de
    passe original ne peut pas etre recupere depuis ce hash ; en cas d'oubli,
    il faut mettre en place une procedure de reinitialisation.

config/DataInitializer.java
    Initialise le compte administrateur de bootstrap selon la configuration
    et desactive les fournisseurs en attente ou refuses qui seraient actifs.
    Les identifiants d'administration doivent etre configures avec des
    valeurs fortes hors du code source, surtout en production.

dto/request/AuthRequest.java
    Corps JSON de connexion : identifiant et motDePasse. L'identifiant est
    l'email pour ADMIN ; AGRICULTEUR, ACHETEUR et FOURNISSEUR peuvent utiliser
    leur email ou leur numero de telephone.

dto/response/AuthResponse.java
    Donnees retournees apres une connexion reussie : token, type Bearer,
    identifiant, nom, prenom, email et role.

reponse/ApiResponse.java, reponse/GlobalResponseAdvice.java
    Format global des reponses de l'API. Les erreurs de validation et les
    erreurs de securite peuvent avoir leur format specifique selon leur
    gestionnaire. La specification OpenAPI doit rester accessible sans etre
    enveloppee dans ApiResponse.

Parcours de connexion et d'une requete protegee
    1. Le client envoie POST /api/auth/login avec un JSON comme :
       {"identifiant":"+22370000000","motDePasse":"mot-de-passe"} ou
       {"identifiant":"acheteur@example.ml","motDePasse":"mot-de-passe"} pour
       un agriculteur, acheteur ou fournisseur, ou
       {"identifiant":"admin@example.ml","motDePasse":"mot-de-passe"} pour
       un administrateur.
    2. AuthController transmet la demande a AuthServiceImpl.
    3. Le service retrouve l'utilisateur, compare le mot de passe fourni a
       son hash BCrypt et verifie l'etat du compte.
    4. JwtUtil genere le token ; AuthResponse le retourne au client. Dans la
       reponse globale, le token se trouve dans data.token.
    5. Le client conserve le token de maniere appropriee et l'envoie ensuite
       sur chaque route protegee dans l'en-tete :
       Authorization: Bearer <JWT>
    6. JwtAuthFilter valide le token et etablit l'identite pour la requete.
       SecurityConfig exige l'authentification ; les annotations
       @PreAuthorize controlent ensuite le role et, si necessaire, le
       proprietaire de la ressource.
    7. La requete autorisee poursuit son parcours Controller -> Service ->
       Repository -> base de donnees ; la reponse revient au client.

Roles et erreurs visibles par le client
    Les roles sont ADMIN, AGRICULTEUR, ACHETEUR et FOURNISSEUR. Etre
    authentifie ne signifie pas avoir le droit d'appeler toutes les routes :
    le role et les regles de propriete sont controles separement.

    HTTP 401 : authentification absente ou invalide, token expire ou
    identifiants incorrects.
    HTTP 403 : utilisateur authentifie mais non autorise, compte desactive
    ou compte fournisseur pas encore valide.

Utilisation depuis Angular, Flutter et Swagger
    Angular peut ajouter automatiquement l'en-tete Bearer avec un HTTP
    interceptor. Flutter peut configurer son client HTTP (par exemple Dio)
    pour ajouter le meme en-tete. Le JWT doit etre conserve de facon adaptee
    a la plateforme, supprime a la deconnexion et transmis uniquement via
    HTTPS en production.

    Dans Swagger, ouvrir Authorize et coller le JWT obtenu a la connexion ;
    ne saisir que le token si l'interface ajoute deja le prefixe Bearer.
    Dans Postman, ajouter Authorization avec le type Bearer Token et coller
    le JWT.
